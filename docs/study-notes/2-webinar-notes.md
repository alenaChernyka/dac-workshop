# Git для техписателя

В распределенной системе контроля версий проект работает на всех устройствах:

- Автономность работы: пользователь работает с локальной копией проекта на своем устройстве.
- Высокая скорость работы: многие операции выполняются локально без подключения к центральному серверу.

## Как работает Git

Коммит — снимок состояния проекта в определенный момент времени, контрольная точка, в которой хранится информация о внесенных изменениях.

Ветка — указатель на определенный коммит, а также последовательность коммитов под этим указателем.

Слияние — процесс добавления изменения из одной ветки в другую.

Целевая и сливаемая ветки (куда и откуда вносятся изменения)

## Области хранения данных в Git

Обязательная последовательность действий при сохранении изменений:

1. Рабочая директория (Working Directory) — сохранение файла
2. Индекс (Stage area) — add
3. Локальный репозиторий (Local Repository) — commit
4. Удаленный репозиторий (Remote Repository) — push

## Практика

### Изменения

1. Настроить

`git config` (при первой установке, с флагом `--global` или без флага для локального изменения) — представиться в гите и добавить почту

2. Получить посление изменения

`git pull` — всегда обязательно сразу забирать изменения

3. Создать рабочую ветку

`git status`

`git brach username-add-new-webinar` (имя + задача) сделать ветку 

!!! note "Примечание"
    Правило хорошего тона: ничего не делать в мастере, работать в отколотых ветках

`git status`

`git switch {название}` переключиться на ветку 

`git status`

3. Сохранить изменения

Сохранить обычно

`git add`

`git status`

`git commit -m ""`

!!! note "Примечание"
    Правило хорошего тона: писать что изменилось.

`git status`

`git push`

`git push --set -upstream origin`

4. Создать pull request

Github: pull request

Название: Добавление ...

Описание: Что сделано

В pull request можно добавлять коммиты.

### Удаление изменений

**Локально:** `git restore {название файла}` или c точкой

**В индексе:** `git restore --staged {название файла}` или c точкой (потом локально)

**В закоммиченных:**
- опасный способ: `git reset HEAD~1` (удаляет коммит, как будто бы его не существовало)
- безопасный способ: `git revert {хэш коммита}`

`git log` — посмотреть историю коммитов с хэшами (идентификаторы —длинные уникальные числа)

### Разрешение конфликтов

`git branch -r` — посмотреть удаленные ветки

Можно сделать merge без pull request — например, влить в свою ветку

`git switch` переключиться на целевую ветку (куда)

`git merge` название сливаемой ветки

Возник конфликт

`git status`

изменить файл (вручную или автоматически — `git checkout -ours` (целевая ветка) или `-theirs` (вливаемая ветка)) имя файла или точка

Сохранить

`git status`

`git add`

`git commit` 

`git push`

## Базовые правила работы с гит

По гиту всё сильно зависит от процессов работы с ним, принятых в команде. Но есть несколько базовых правил:

1. Выполнять git pull перед началом работы
2. Не удалять коммиты безвозвратно (не использовать git reset)
3. Вместо удаления отменять коммиты (использовать git revert)
4. Не публиковать изменения принудительно (не использовать команду git push --force) — это может затереть чужие изменения в ветке
5. Не пушить напрямую в ветку master/main и в другие важные ветки в проекте (их может быть несколько, например, отдельная ветка для релизов)
